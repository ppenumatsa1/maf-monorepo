## Reconciliation ownership boundary

The prior analysis found that a provision preview would reconcile shared
resources that this lane must retain: the Container Apps environment, ACR,
Foundry account/project/model deployments, monitoring, and Foundry
connections. The repaired template treats its required ACR, environment,
Foundry, model, and Application Insights resources as existing dependencies and
does not declare PostgreSQL, evaluation storage, monitoring configuration, or
Foundry connections.

Only the lane-specific frontend and backend Container Apps, their
registry-pull identity, and their required resource-scoped role assignments
remain declarative. The database remains an existing TLS connection-string
dependency and is not a Bicep resource.

## Gated release DAG

Run `make foundry-release` only from an authenticated operator workstation and
only after the recipe validation below is recorded.

1. The deployment-mode router inspects tracked and untracked changes against
   `FOUNDRY_RELEASE_BASE_REF`. Every automatic route is `app_only`.
   Infrastructure, package, Make, and release-script changes select full local
   validation; application changes also select full validation; documentation
   changes select quick validation.
2. The selected validation target and `make foundry-iac-build` run
   concurrently. Both must succeed.
3. `app_only` deliberately skips provisioning. `make foundry-provision` can
   run only when an operator supplies
   `FOUNDRY_INFRA_RECONCILIATION_APPROVED=true` and a non-secret
   `FOUNDRY_INFRA_RECONCILIATION_REFERENCE` after preview review. Neither path
   permits database creation or rebuild.
4. `make foundry-release-deploy` performs a fresh hosted-source sync and
   `azd package --no-prompt`, verifies PostgreSQL readiness exactly once, then
   runs the backend, frontend, and hosted-agent deployment legs in parallel
   independently.
5. The Foundry project Application Insights connection is verified, then the
   high-risk Responses smoke gate runs.
6. Trace evaluation starts after smoke while hosted E2E runs. The evaluation
   launcher waits for E2E evidence generated by this release; the evaluator
   retains its configured HITL trace-age wait and accepts only explicit
   `completed` evaluation status.
7. Hosted E2E must write fresh evidence before telemetry begins. Telemetry may
   overlap the remaining evaluation polling, but must correlate only the E2E
   run evidence from this release.
8. The release prints completion only after both evaluation and telemetry
   succeed. Record the proof in the delivery ledger.

The DAG reduces wall-clock time only where prerequisites permit it. It does not
turn an app-only deployment into an authorization to create, replace, or
reconfigure a retained resource, and it does not allow evaluation or telemetry
to rely on a stale E2E artifact.

## Azure validation recipe

These commands are an operator recipe, not evidence that they were run here.
They do not authorize a deployment.

```bash
# Static preflight
bash -n scripts/foundry/*.sh scripts/skills/*.sh
make foundry-iac-build
FOUNDRY_RELEASE_BASE_REF=<approved-base> \
  ./scripts/skills/deployment-mode-router.sh "$FOUNDRY_RELEASE_BASE_REF"

# Azure validation: preview only; review every proposed change before continuing.
cd infra/foundry-hosted
azd provision --preview --no-prompt
cd ../..

# Fresh package validation must use a newly synced hosted context.
make foundry-package
```

For `azure-validation`, also confirm the selected subscription/environment,
the existing server state and TLS/firewall readiness, the Foundry project
Application Insights connection, and the Bicep-declared role scopes. If a
preview includes database replacement, unreviewed RBAC change, public-access
weakening, or any unexpected resource change, stop and record the blocker.
